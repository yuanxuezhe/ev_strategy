# 04 周期合并机制（最核心机制）

> 相关源码：`compute_bucket`（`mysql_analyze_demo.py:70-82`）、`_bucket_plus_period`（`mysql_analyze_demo.py:64-67`）、`BarAggregator`（`mysql_analyze_demo.py:91-146`）

## 1. 目标

把 1m 原始 bar 流**增量**合并成目标周期（5m/15m/...）K 线：
每来一根 1m bar，立刻能拿到"最新周期 K 线"，不重算历史——这是回测与实盘（逐根推送）能共用一套代码的前提。

## 2. `compute_bucket` —— 该 bar 属于哪个桶

**约定：前开后闭区间 `(prev, ts]`，桶 ts 标注右端点**（与通达信等软件一致：一根 10:05:00 收盘的 5m K 线，ts 就是 10:05:00）。

三步算法（`mysql_analyze_demo.py:70-82`），以 5m（pos=10，取分钟字段）为例，输入 `stime="20250105100730"`：

1. **取字段**：`num = int(stime[pos:pos+2])` → `"10"` → 10（分钟）
2. **向下取整造 floor**：`floor = stime[:pos] + f"{(num // value) * value:02d}" + "0" * 后续位数`
   → `10 // 5 * 5 = 10`，秒位补 0 → `"20250105101000"`（floor = 所属区间的左端点）
3. **边界判断**：
   - 若 `num % value == 0` **且** pos 之后所有位全 0（本例 `"730"` 不满足）→ 该 bar 恰好踩在边界上，`ts = floor`
   - 否则 `ts = floor + 周期` → `"20250105101000"` + 5min = `"20250105101500"`

即：10:07:30 这根 bar 属于区间 `(10:05, 10:10]`，桶 ts = **10:10:00**。

### 各周期示例（桶 ts）

| bar 的 stime | 5m 桶 ts | 说明 |
|---|---|---|
| 20250105100500 | 10:05:00 | 整除且秒为 0 → 边界，右端点即自身 |
| 20250105100730 | 10:10:00 | floor 10:05 + 5m |
| 20250105100459 | 10:05:00 | floor 10:00 + 5m |

| bar 的 stime | 1h 桶 ts | 说明 |
|---|---|---|
| 20250105090000 | 09:00:00 | 边界 |
| 20250105093500 | 10:00:00 | floor 09:00 + 1h |

| bar 的 stime | 1d 桶 ts | 说明 |
|---|---|---|
| 20250105093500 | 2025-01-06 00:00:00 | 全天 bar 属于 `(1月5日0点, 1月6日0点]` |
| 20250105000000 | 2025-01-05 00:00:00 | 恰好午夜边界（罕见） |

### 两个实现细节

- **为什么 floor+周期 用 datetime 进位而不是字符串加**：字符串加法会遭遇 60 秒/24 时/月末日等溢出边界；`(datetime.strptime(floor) + delta).strftime(...)` 天然正确（`mysql_analyze_demo.py:67`）。
- **为什么包一层 `lru_cache(maxsize=200000)`**：同一周期桶的 ts 计算会被桶内每根 1m bar 重复调用（一根 5m 桶被算约 5 次，结果相同），缓存键 `(floor字符串, delta)` 命中率极高（`mysql_analyze_demo.py:64`）。

## 3. `BarAggregator` —— 桶生命周期

状态：`bars: list[dict]`（**全部**已闭合桶，整个回测期间持续增长）、`cur: dict | None`（当前未闭合桶）。

`update(bar)` 的处理顺序（`mysql_analyze_demo.py:108-139`）：

1. 算 ts、算 mark（`stime < warmup_until` → 0，否则 1）
2. **桶切换判断**：`ts != cur["ts"]` → 旧桶快照 append 进 `bars`，`cur = None`
3. **新桶**：初始化 dict（open/high/low/close/volume 取本根，count=1，mark=本根）
   **同桶**：`high=max`、`low=min`、`close=最新`、`volume+=`、`count+=1`、`mark=最新`
4. **回调**：`bars.append(cur)` → `on_bars(bars)`（此时末位是当前桶最新合并结果）→ `finally: bars.pop()`

> 用 append/pop 复用 `bars` 列表，避免每次回调都做 `self.bars + [self.cur]` 的 O(n) 拷贝（`mysql_analyze_demo.py:133-139` 注释）。

`flush()`（`mysql_analyze_demo.py:141-146`）：数据流结束时把最后一个未闭合桶收入 `bars` 并再回调一次 `on_bars`，保证最后一根周期 K 线不丢。

### 回调契约

`on_bars(bars)` 收到的列表 = **已闭合桶们 + 当前桶（末位）**：

- `bars[:-1]` = 已闭合桶（自旧到新）
- `bars[-1]` = 当前桶（尚未收完，但 H/L/C 已是最新行情）
- Engine 依赖这个契约拆分（见 09 文档），**自定义 on_bars 必须遵守同一约定**

### mark 与预热

- `warmup_until` 是一个 stime 字符串阈值（回测中 = 策略起始日 `000000`）
- `stime < warmup_until` 的 bar 属于预热：**合并与指标照常进行，但不驱动策略**
- 同桶内 mark 跟随最新一根 → 一根桶只在"最后一根 1m bar 仍属预热期"时才算预热桶

## 4. 复杂度与内存

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 每根 1m bar 合并 | O(1) | dict 字段更新 + ts 计算（lru_cache 命中） |
| 桶切换 | O(1) | append 快照 |
| 每次回调 | O(1) 传引用 | append/pop，不拷贝列表 |
| 内存 | O(闭合桶数) | `bars` 保留全部闭合桶（策略/指标需要全量历史；也是回测后复盘的现成数据） |

## 5. 任意周期支持 (2026-09-05 升级)

桶算法已升级为**本地锚定 epoch 取整**的通用实现 (`compute_bucket_general` /
kernel.`bucket_ts_encoded`), 支持任意 `数字+m/h/d` 周期 (7m/90m/2h/6h/3d/7d...):

```
e  = bar 的 naive-epoch 秒   (stime 即北京墙钟, 午夜天然对齐 86400 倍数)
e0 = (e // P) × P            (P = 周期秒数)
桶 ts = e0 (恰在边界) 或 e0 + P (前开后闭, 右端点标注)
```

- **老 7 周期行为不变**: 能整除天长的周期 (5m/15m/30m/1h/2h/4h/1d...) 边界恰好
  落在同一钟面位置, 与原字段取整算法**逐例等价** (tests/test_timeutils.py 锁定)。
- **为什么必须升级**: 原字段取整算法对 >60m 周期分区错误 (分钟字段 0-59 无法对
  90 取整, 桶会重叠), 对 3d 在月初直接崩溃 (拼出 day=00 非法日期)。
- **不整除天长的周期** (如 7m, 86400%420=300): 边界相对钟面每日漂移 5 分钟,
  分区仍连续无重叠、确定 —— 这是周期本身的性质, 与加密交易所做法一致。
- 入口: `resolve_period_seconds("90m") -> 5400` (带格式校验); CLI `--period 90m`
  与 `--grid "period=30m,90m,2h"` 均已支持; 参考引擎 (ref) 与内核同算法。

## 6. 易错点

1. **桶 ts 是右端点**：做时间对齐、与外部数据 join 时，`10:15:00` 的 5m 桶实际覆盖 `(10:10, 10:15]`。
2. **1d 桶 ts 是次日 00:00:00**（除恰好午夜的 bar 外），不要当成"当天 0 点开盘桶"。
3. **闭桶只会追加不会修改**：闭合桶是快照；但**当前桶**的字段每根 bar 都在变，异步消费时注意一致性。
4. **warmup 判断用原始 bar 的 stime**，不是桶 ts。
