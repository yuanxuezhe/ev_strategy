# 02 系统架构

> 相关源码：`Engine`（`evtrade/core/engine.py`）、向量化引擎
> （`evtrade/core/vectorized_engine.py`）、CLI 入口 `main`（`evtrade/cli.py`）；
> 历史背景：旧 DSL/numba 三端路径已下线，本文档为 2026-09-09 统一 CPU/GPU 重构版。

## 1. 分层架构总图

```
                     ┌────────────────────────────────────────────────┐
   数据层            │  MySQL minute_bars (1m 原始行情)                │
                     └───────────────┬────────────────────────────────┘
                                     │ SQL 分段查询 (7天/段, 含预热)
   行情源层  ┌───────────────────────▼───────────────────────┐
   (Feed)    │  MySQLBacktestFeed / ChainedFeed / (LiveFeed) │  统一 yield Bar
             └───────────────────────┬───────────────────────┘
                                     │ Bar (stime/code/OHLCV)
   合并层    ┌───────────────────────▼───────────────────────┐
             │  BarAggregator  1m → 目标周期桶               │  update(bar)
             │  compute_bucket 定桶 + 桶生命周期管理          │
             └───────────────────────┬───────────────────────┘
                                     │ on_bars(闭合桶..., 当前桶)   ← 每根 1m bar 都回调
   引擎层    ┌───────────────────────▼───────────────────────┐
             │  Engine.on_bars                               │
             │   ├─ mark=0 预热: 仅驱动策略 (FSM 累积)        │
             │   └─ mark=1 策略期: 桶 CLOSE 时用上一桶       │
             │      finalized OHLCV → step(state, bar)
             └───────────────────────┬───────────────────────┘
                                     │ sig ∈ {-1, 0, 1}
             ┌───────────────────────▼───────────────────────┐
   策略层    │  VectorizedStrategy.step(state, bar,…)   │
             │   ├─ ema_channel_step (策略 step 内增量)        │
             │   ├─ 偏离 + 锁存 FSM (Python 循环)            │
             │   └─ step(state, bar) 单方法           │
             │      state 由 engine 持有 (dataclass)         │
             └───────────────────────┬───────────────────────┘
                                  │ signal (+ info dict)
   展示层    ┌────────────────────▼───────────────────────────┐
             │  strategy.format_signal_line(cur, signal, info)│  信号行打印 (hook, 无 positional 指标)
             └────────────────────────────────────────────────┘
   执行层    ┌────────────────────▼───────────────────────┐
             │  SimulatedExecutor (回测)                   │
             │  BrokerExecutor (实盘占位)                  │
             └────────────────────┬───────────────────────┘
                                  │ apply(side, qty, price, ts)
   账户层    ┌────────────────────▼───────────────────────┐
             │  Account  cash / position / trades          │
             └─────────────────────────────────────────────┘
```

> 框架只喂 OHLCV；EMA / ATR / Bollinger / RSI 等所有指标由策略
> 通过 `evtrade/indicators/` xp 算子或纯 Python 增量 API 自维护。
> framework **不假定任何指标字段名**（参见 CLAUDE.md §5 与
> `openspec/specs/evtrade-architecture/spec.md` 的 "Indicators are private to strategies" Requirement）。

## 2. 组件职责与依赖

| 组件 | 职责 | 依赖谁 | 被谁依赖 |
|---|---|---|---|
| `Feed` 及其实现 | 按时间从旧到新 yield `Bar` | 数据库 / 其他源 | Engine |
| `BarAggregator` | 1m → 周期桶合并；管理桶生命周期；打 mark | `compute_bucket`、`PERIODS` | Engine 持有 |
| `VectorizedStrategy` (`evtrade/strategies/vectorized_base.py`) | 唯一策略基类; 唯一抽象 `step(state, bar, params) -> (state, sig)`; 持久状态由 engine 持有 (`@dataclass`, 如 channel_deviation 的 `ChannelDeviationState`); 策略无 instance attr | `evtrade/indicators/*` (xp + step) | `vectorized_engine.run_vectorized` / `Engine.on_bars` / `core/sweep.py` / `core/replay.py` |
| `Account` | 资金/持仓记账、权益计算 | 无 | Executor |
| `Executor` | 把信号变成"成交"（模拟或真实） | Account | Engine |
| `Engine` | 装配全部组件, 串联回调链, 驱动逐 bar 路径 (实盘/对账) | 上述全部 | `main` / `replay_engine` |

> 框架层**无** `EMAChannel` / `IncrementalEMA` / `KernelState` 组件；
> EMA / FSM 等都是策略私有 state (dataclass 字段), 由 `step(state, bar, params)` 内部维护。
> **state 由 engine 持有**, 策略无 instance attr (strategy-step-only, 2026-09-10)。

关键解耦设计：

- **合并器不知道策略**：`BarAggregator` 只负责合并，通过 `on_bars` 回调把"周期 K 线集合"交给外部（`evtrade/core/aggregator.py`）。
- **策略不知道行情源与账户**：`VectorizedStrategy.step(state, bar, params) -> (state, sig)`
  规范接口只收 `(state, bar, params)`; framework 通过 `Engine.on_bars` 循环调 step 触发;
  策略需要的任何指标都在 `step` 内部通过 `evtrade/indicators/*.step(...)` 自维护。
- **账户不知道下单方式**：`Account.apply` 纯记账，由 Executor 决定何时以什么价格调它。
- **Engine 是唯一装配点**：构造时把 `aggregator.on_bars` 覆写为自己的 `on_bars`，完成接线。

## 3. 一次回调的完整数据流

### 3.1 向量化路径 (vectorized_engine.run_vectorized)

```
bars_1m (1m bar 数组) → _aggregate_buckets_xp (xp 向量化分桶)
                       → engine 循环 strategy.step(state, bar, params)
                       → sig × mark → 预热段清0
                       → _execute_trades (signals → trades + equity_curve)
                       → metrics.summarize → summary (30 字段)
```

### 3.2 逐 bar 路径 (Engine.on_bars)

1. `Engine.run()` 从 `feed.stream()` 取一根 `Bar`
2. `aggregator.update(bar)`:
   - `compute_bucket` 算出该 bar 属于哪个周期桶 ts
   - 同桶合并 H/L/C/V; 桶切换时把旧桶收入 `self.bars` (闭合桶列表)
   - 以 `闭合桶 + [当前桶]` 调 `on_bars`
3. `Engine.on_bars(bars)` (`engine.py:47`):
   - `cur = bars[-1]`; 桶切换时 (`self._last_cur["ts"] != cur["ts"]`) 用**上一桶 finalized OHLCV**
     驱动一次 `strategy.step(state, bar)(np, prev, params)`
   - mark=0 (预热) 跳过驱动
   - mark=1 时若有信号 → `executor.trade(signal, price, prev["ts"])`
   - verbose 时通过 `strategy.format_signal_line(prev["ts"], sig, info)` 打印
4. 循环结束 (`aggregator.flush()` + `_flush_final_bucket()`) 输出最后桶信号
5. `print_summary()` 输出盈亏

> **桶 CLOSE 语义**：Engine 在桶**切换**那一刻（看到当前根 `ts` ≠ 上一根 `ts`）
> 才用**上一桶 finalized OHLCV** 驱动策略一次。这样与 vectorized 路径在"桶级 finalized OHLCV"
> 上计算指标完全对齐（reconcile 测试通过 `bucket_diff_cap=8` 容忍 EMA 累积漂移）。
> 详见 `core/replay.py::reconcile`。

## 4. 回测 / 实盘切换原则

框架的设计目标写在文件头：**换 Feed + 换 Executor，其余不变。**

| 场景 | Feed | Executor | 其余 |
|---|---|---|---|
| 回测（当前 `main` 实现） | `MySQLBacktestFeed`（历史分段 + 预热） | `SimulatedExecutor`（当根 close 成交） | 不变 |
| 实盘（预留） | `ChainedFeed(MySQLBacktestFeed(...今天), LiveFeed(code))` | `BrokerExecutor`（接券商 API） | 不变 |

- `ChainedFeed` 先播历史预热数据再接实时流，保证实盘启动时指标已预热（`evtrade/feeds/chained.py`）
- `BrokerExecutor` 目前是占位实现，打印 `[LIVE]` 日志并返回 False，接入点见 07 文档
- 实盘时 Feed 需要实现同样的 `stream() -> Iterator[Bar]` 接口，把实时 tick/1m bar 转成统一 `Bar` 结构

## 5. 时序（信号触发一瞬）

```
向量化路径 (vectorized):
  bars_1m → _aggregate_buckets_xp (桶级 OHLCV)
         → engine 循环 step(state, bar, params) → sig[N]
         → sig[mark==1] → _execute_trades → trades
         → metrics.summarize(equity_curve, ...) → summary (30 字段)

逐 bar 路径 (Engine.on_bars, 实盘 / 对账):
  Bar(10:07:30) → aggregator.update
      → ts = compute_bucket("...100730", 5m) = 10:10:00   (前开后闭右端点)
      → 同桶合并: H/L/C/V 更新
      → on_bars(closed + [cur])
          → cur.ts != last_cur.ts → 桶切换:
              prev = last_cur (finalized OHLCV)
              price = prev["close"]
              executor.update_price(price)
              sig = strategy.step(state, bar)(np, prev, params)
              if sig: executor.trade(sig, price, prev.ts)
              if verbose: print(format_signal_line(...))
```

EMA 增量状态由 engine 持有 (`Engine._state: ChannelDeviationState` dataclass),
`step(state, bar, params)` 内部调 `ema_step(state.ema, h, l, tf1)` 维护;
**framework 持有 state, 策略无 instance attr** (strategy-step-only, 2026-09-10)。

## 6. 与旧架构的差异

| 维度 | 旧 DSL/numba 三端 (2026-09-08) | 现状 (2026-09-10 step + torch) |
|---|---|---|
| 策略主逻辑 | docstring DSL body | Python class 覆写 `step(state, bar, params)` |
| 渲染层 | Python exec + numba @njit + CUDA C99 | 无 (Python + torch) |
| 性能路径 | numba (CPU) / CUDA (GPU) | torch (CPU) / torch (CUDA) |
| 单 bar 入口 | `StrategyBase.check(cur, {})` | `step(state, bar, params)` |
| 持久状态 | `state_spec` AST 白名单 + 三端投影 | `@dataclass` state 由 engine 持有 |
| `Engine.on_bars` | `strategy.check(cur, {})` | 桶 CLOSE 语义, 用 `prev` finalized OHLCV 驱动 |
| 回测指标 | kernel 内置 + 部分占位 | `metrics.summarize` 完整 30 字段 (含 x_mdd; cagr / sharpe / sortino / calmar / max_dd_days / ...) |
