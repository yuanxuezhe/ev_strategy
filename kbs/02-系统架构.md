# 02 系统架构

> 相关源码：`Engine`（`evtrade/core/engine.py`）、CLI 入口 `main`（`evtrade/cli.py`）；
> git 历史原始行号对应 `mysql_analyze_demo.py:516-625` / `:637-680`（commit 5585371）。

## 1. 分层架构总图

```
                     ┌────────────────────────────────────────────────┐
   数据层            │  MySQL minute_bars (1m 原始行情)                │
                     └───────────────┬────────────────────────────────┘
                                     │ SQL 分段查询 (7天/段, 含预热)
   行情源层  ┌───────────────────────▼───────────────────────┐
   (Feed)    │  MySQLBacktestFeed / ChainedFeed / (LiveFeed) │  统一 yield Bar
             └───────────────────────┬───────────────────────┘
                                     │ Bar (stime/code/OHLCV)
   合并层    ┌───────────────────────▼───────────────────────┐
             │  BarAggregator  1m → 目标周期桶               │  update(bar)
             │  compute_bucket 定桶 + 桶生命周期管理          │
             └───────────────────────┬───────────────────────┘
                                     │ on_bars(闭合桶..., 当前桶)   ← 每根 1m bar 都回调
   引擎层    ┌───────────────────────▼───────────────────────┐
             │  Engine.on_bars                               │
             │   ├─ mark=0 预热: 只 _sync_ema (累积指标)      │
             │   └─ mark=1 策略期: ↓                         │
             └───────┬───────────────────────┬───────────────┘
                     │ EMAChannel.channel    │ ChannelDeviationStrategy.check
   指标/策略层        │ (UP, DW) O(1)         │ (cur, indicators) → (signal, info) 锁存逻辑
             └───────┴───────────┬───────────┴───────────────┘
                                  │ BUY / SELL  (+ info dict)
   展示层    ┌────────────────────▼───────────────────────────┐
             │  strategy.format_signal_line(cur, signal, info)│  信号行打印 (hook, 无 positional 指标)
             └────────────────────────────────────────────────┘
   执行层    ┌────────────────────▼───────────────────────┐
             │  SimulatedExecutor (回测)                   │
             │  BrokerExecutor (实盘占位)                  │
             └────────────────────┬───────────────────────┘
                                  │ apply(side, qty, price, ts)
   账户层    ┌────────────────────▼───────────────────────┐
             │  Account  cash / position / trades          │
             └────────────────────────────────────────────┘
```

## 2. 组件职责与依赖

| 组件 | 职责 | 依赖谁 | 被谁依赖 |
|---|---|---|---|
| `Feed` 及其实现 | 按时间从旧到新 yield `Bar` | 数据库 / 其他源 | Engine |
| `BarAggregator` | 1m → 周期桶合并；管理桶生命周期；打 mark | `compute_bucket`、`PERIODS` | Engine 持有 |
| `EMAChannel` | 维护上/下轨增量 EMA，O(1) 输出 (UP, DW) | `IncrementalEMA` | Engine |
| `ChannelDeviationStrategy` (`evtrade/strategies/channel_deviation.py`) | DSL 策略; 输入 `(cur, indicators: dict)` → `(signal, info)`; 持久状态由 `state_spec` 声明 (低/高 hit 锁存 + lock_ts + 低/高 acted) | 无（纯状态机 + DSL ctx） | Engine (ref) / `core/kernel.py` DSL 特化内核 (numba) / `core/gpu.py::cuda_sweep_window_generic` (CUDA) |
| `Account` | 资金/持仓记账、权益计算 | 无 | Executor |
| `Executor` | 把信号变成"成交"（模拟或真实） | Account | Engine |
| `Engine` | 装配全部组件，串联回调链，驱动运行 | 上述全部 | `main` |

关键解耦设计：

- **合并器不知道策略**：`BarAggregator` 只负责合并，通过 `on_bars` 回调把"周期 K 线集合"交给外部（`evtrade/core/aggregator.py`）。
- **策略不知道行情源与账户**：`StrategyBase.check` 规范接口是 `(cur: dict, indicators: dict) → (signal|None, info)`；
  `ChannelDeviationStrategy.check` 兼容旧 `(cur, up, dw)` 调用（`channel_deviation.py:99`），但框架对其他消费方
  （kernel / GPU）的 ctx 字段已统一通过 `bundle_per_bar` 打包为 `per_bar` dict，**不再命名指标字段**。
- **账户不知道下单方式**：`Account.apply` 纯记账，由 Executor 决定何时以什么价格调它。
- **Engine 是唯一装配点**：构造时把 `aggregator.on_bars` 覆写为自己的 `on_bars`（`engine.py:53`），完成接线。

## 3. 一次回调的完整数据流（逐根 1m bar）

1. `Engine.run()` 从 `feed.stream()` 取一根 `Bar`（`engine.py:98`）
2. `aggregator.update(bar)`（`core/aggregator.py`）：
   - `compute_bucket` 算出该 bar 属于哪个周期桶 ts
   - 新桶则初始化、旧桶则合并（H 取极值、C 取最新、V 累加）
   - 若桶切换，先把旧桶快照收入 `self.bars`（闭合桶列表）
   - 以 `闭合桶 + [当前桶]` 调用 `on_bars`（用 append/pop 复用列表，避免 O(n) 拷贝）
3. `Engine.on_bars(bars)`（`engine.py:63`）：
   - `closed = bars[:-1]`，`cur = bars[-1]`
   - `_sync_ema(closed)`：把**新增的**闭合桶 push 进 EMA 状态（用 `_pushed` 计数保证幂等）
   - 若 `cur["mark"] == 0`（预热期）→ 到此为止，只累积指标
   - 策略期：`price = cur["close"]` 更新账户 last_price → `ema_ch.channel(cur_h, cur_l)` 得 (UP, DW) → `strategy.check(cur, up, dw)` 得信号 → 有信号则 `executor.trade(signal, price, cur["ts"])`；verbose 时通过 `strategy.format_signal_line(cur, signal, info)` 打印（`engine.py:92-96`，hook 签名无 positional 指标）
4. 循环结束（或 Ctrl+C）后 `aggregator.flush()` 收尾闭合最后一个桶，最后 `print_summary()` 输出盈亏

> 内核 / replay 路径下，per-bar 数组由 `kernel.bundle_per_bar` / `replay` 打包为 `{"sig":..., "per_bar":{"up","dw","ts","o","h","l","c","v"}}` 的 dict 契约（见 12 号文档 2.6 节）；framework / CLI / 策略 hook 按需取值，不出现指标键名作为函数关键字参数。

## 4. 回测 / 实盘切换原则

框架的设计目标写在文件头：**换 Feed + 换 Executor，其余不变。**

| 场景 | Feed | Executor | 其余 |
|---|---|---|---|
| 回测（当前 `main` 实现） | `MySQLBacktestFeed`（历史分段 + 预热） | `SimulatedExecutor`（当根 close 成交） | 不变 |
| 实盘（预留） | `ChainedFeed(MySQLBacktestFeed(...今天), LiveFeed(code))` | `BrokerExecutor`（接券商 API） | 不变 |

- `ChainedFeed` 先播历史预热数据再接实时流，保证实盘启动时指标已预热（`evtrade/feeds/chained.py`）
- `BrokerExecutor` 目前是占位实现，打印 `[LIVE]` 日志并返回 False，接入点见 07 文档
- 实盘时 Feed 需要实现同样的 `stream() -> Iterator[Bar]` 接口，把实时 tick/1m bar 转成统一 `Bar` 结构

## 5. 时序（信号触发一瞬）

```
Bar(10:07:30) → aggregator.update
    → ts = compute_bucket("...100730", 5m) = 10:10:00   (前开后闭右端点)
    → 同桶合并: H/L/C/V 更新, mark 跟随最新
    → on_bars(closed + [cur])
        → _sync_ema (无新增闭合桶则空转)
        → mark=1 → channel(cur.H, cur.L) → (UP, DW)
        → strategy.check(cur, UP, DW)
            例: low_hit 已置位 且 low_dev_h < 1.0 → signal="BUY"
        → executor.trade("BUY", cur.close, cur.ts)
            → SimulatedExecutor: qty=min(10000, cash/price)
            → account.apply("BUY", qty, price, ts)  现金减少、持仓增加
```
